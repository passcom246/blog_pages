前端性能优化清单 ​

性能优化最容易犯的错，是在收益最低的地方花最多时间。这份清单按「投入产出比」排序。

一、图片：收益最高，改动最小 ​

图片往往占页面体积的 70% 以上，而优化成本几乎为零：

html
<!-- 首屏之外的图片一律懒加载 -->
<img src="cover.webp" alt="封面" loading="lazy" decoding="async" />
1
2

VitePress 项目可以在配置里全局开启：

ts
// docs/.vitepress/config.mts
export default defineConfig({
  image: { lazyLoading: true }
})

3
4

配套的两件事：

  1. 用固定宽高比占位，避免图片加载完成时页面跳动：
    css
    .post-card__cover {
  aspect-ratio: 16 / 9;
}
    1
    2
    3
  2. 静态资源走 CDN。博客这类低频更新的站点，图片交给 jsDelivr 之类的图床，源站只出 HTML/CSS/JS。

二、字体：别让用户等字体 ​

中文字体动辄几 MB，全量加载基本等于劝退。务实做法是只用系统字体：

css
--vp-font-family-base: 'Inter', -apple-system, BlinkMacSystemFont,
  'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', sans-serif;
1
2

系统字体零请求、零闪烁，中文渲染质量还比大部分 Web Font 好。

三、构建产物：把大依赖挡在首屏外 ​

  • 能用静态导入的不用动态导入，但大而不急的模块要拆出去（图表、编辑器、代码高亮的多语言包）
  • 检查 dist/assets 里有没有异常大的 chunk，那通常意味着某个依赖被整包引入了
  • 静态站点开启 gzip / brotli，GitHub Pages 会自动处理

四、交互反馈：感知性能也是性能 ​

  • 点击后 100ms 内必须有视觉反馈，哪怕只是一次 :active 状态变化
  • 路由切换时给出过渡，而不是白屏
  • 骨架屏优于转圈：它让用户知道「内容马上就来」
css
.post-card:active {
  transform: translateY(-1px);
}
1
2
3

五、别做过度优化 ​

以下这些，除非有明确的指标支撑，否则不建议做：

  • 为了减少一次请求而把 CSS 全部内联
  • 手动实现虚拟列表（除非真的有上千条数据）
  • 用一堆 will-change 换取微小提升（它本身也消耗内存）

优化的前提是度量。 先看 Lighthouse 和真实用户指标，再决定动哪里。

小结 ​

优先级事项预期收益
高图片懒加载 + 固定宽高比首屏体积、稳定性
高系统字体请求数、渲染闪烁
中代码分割首屏 JS 体积
中交互反馈感知性能
低微观性能调优需要数据支撑

这份清单不追求全面，只追求「照着做就有用」。
